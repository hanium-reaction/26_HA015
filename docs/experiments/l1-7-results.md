## 0. 한 줄 요약

**가설 H1-7A 는 지지되지 않는다 — 그리고 그 반대 방향의 문제가 드러났다.**

LLM 원안은 세션 길이 상한을 대체로 지키고(macro **0.873**) 대기 단계 백스톱에 한 건도
걸리지 않는다(0/1342). 여기까지는 "룰이 없어도 원안이 이미 제약을 지킨다" 다.

그런데 **분량이 일관되게 부족하고, 룰은 그것을 보충하지 않는다.**

- 프롬프트 분량 지시 미달 **83/102**, 최종 커버리지 예산 미달 **85/102** (§2.1)
- 그런데 ③층이 leaf 를 더한 것은 **102행 중 5행뿐**이고 그것도 `busy-thin`·`busy-overflow`
  **두 케이스에서만** 일어난다 (§3)
- 즉 **과소 생성은 보정되지 않고 사용자에게 그대로 도달한다**

⚠️ **그리고 이 수치들의 상당 부분은 설계 산물이다.** 32/34 케이스에서 프롬프트의 "평균
세션 길이" 와 "세션 길이 상한" 이 **같은 숫자**로 인쇄된다. 그러면 개수를 지키고 상한을
안 넘는 순간 분량 비율은 **산술적으로 1.0 을 넘을 수 없다** — 102행 중 88행이 그 상태다.
"과소 생성 83~85건" 은 모델의 행동이라기보다 **골든셋 슬롯 구성의 성질**에 가깝다(§6.1).

## 2. 결과 — micro / macro 이중 집계

§5 는 M17~M26 을 micro·macro **둘 다** 보고하라고 못박는다. 사유도 적혀 있다 —
*"micro 만 보고하면 실제 체감보다 좋아 보인다."* 실측이 정확히 그렇다.

| 지표 | micro | **macro** | 분모 |
|---|---|---|---|
| **M17** 세션 길이 밴드 안 | 0.974 (1307/1342) | **0.873 (89/102)** | leaf / 계획 |
| **M19** 절단 없음 | 0.996 (절단 6개) | 0.980 (100/102) | 〃 |
| **M25** 대기 단계 없음 | **1.000 (0/1342)** | 1.000 (102/102) | 〃 |
| M17·M19·M25 **동시** 통과 | — | **0.853 (87/102)** | 계획 |

micro 0.974 → macro 0.873 의 격차가 §5 가 경고한 그것이다. leaf 하나만 벗어나도 그
계획은 사용자에게 "지켜지지 않은 계획" 이다.

**M17 분해** — 상한 초과 35/1342(0.026), **하한 미달 0/1342**. 실패는 한 방향뿐이다:
LLM 은 세션을 너무 짧게 만들지 않고, 가끔 너무 길게 만든다.

### 2.1 M18 — 두 개로 나눠 읽어야 한다

⚠️ **1차 문서는 이 둘을 하나로 뭉쳤다.** 독립 검토가 지적한 자리다. 프롬프트가 LLM 에게
요구한 분량과 최종 계획의 예산이 **같지 않다** — 앞의 것(`llm_minute_target`)은 세션 수
상한(`_MAX_LLM_SESSIONS`)에 묶여 있어서, 상한이 걸린 케이스에서는 요구량이 예산보다 작다.

| | 무엇을 묻는가 | 중앙값 | 1.0 미만 | =1.0 | 초과 |
|---|---|---|---|---|---|
| **M18a** 프롬프트 분량 준수 | LLM 이 **자기가 받은 지시**를 지켰는가 | 0.947 | **83** | 15 | 4 |
| **M18b** 최종 커버리지 부족 | 원안이 **최종 예산**에 얼마나 못 미치는가 = 룰의 보충 필요량 | 0.946 | **85** | 15 | 2 |

두 값이 갈리는 케이스는 **`busy-thin`·`busy-overflow` 둘뿐**이다(각 3행, 총 6행):

```
busy-thin       프롬프트 요구  200분  vs  최종 예산  280분   → M18b 달성 상한 0.714
busy-overflow   프롬프트 요구 1800분  vs  최종 예산 2160분   → M18b 달성 상한 0.833
```

**이 두 케이스는 M18b 로는 구조적으로 1.0 에 닿을 수 없다.** 그 미달을 LLM 탓으로 읽으면
안 된다 — 프롬프트가 애초에 그만큼을 요구하지 않았다.

§5 의 읽는 규칙이 명시적이다 — *"M18 이 1.0 미만이면 '제약을 지킨 것'이 아니라 **과소
생성**으로 읽는다."* 두 지표 모두 그 규칙을 그대로 적용한 값이다.

⚠️ **1차 실행은 이것을 "미달 3건" 으로 보고했다.** `< 0.8` 이라는, 사전등록 어디에도 없는
임계값을 썼기 때문이다(§5 정정 표 2번).

**말할 수 있는 것과 없는 것**

- ✅ *"원안이 최종 커버리지 예산에 못 미쳐 룰의 보충이 필요한 계획이 85/102 다"* — M18b
- ✅ *"LLM 이 프롬프트의 분량 지시를 못 채운 계획이 83/102 다"* — M18a
- ❌ *"LLM 이 분량 지시를 85/102 번 무시했다"* — **두 주장을 섞은 것.** 1차 문서의 표현이었다

### 2.2 블록별 — `milestone_fixed` 가 가장 나쁘다

| 블록 | n | leaf | M17 micro | **M17 macro** | M18 중앙 | M18<1.0 | M19 |

마일스톤이 붙은 케이스에서 macro 가 **0.722** 로 떨어진다. 마일스톤을 branch 로 고정하라는

## 3. F21 룰 개입량 폭포 — 그리고 이 그림의 한계

```
0_llm_raw                13.16
1_waiting_dropped        13.16   (변화 없음)
2_out_of_cycle_dropped   13.16   (변화 없음)
3_shaped                 13.10   (-0.06)
4_extended               13.30   (+0.20)
→ LLM 원안 13.16 → 최종 13.30   (룰이 만든 몫 +0.15)
```

⚠️ **이 폭포는 개수만 세므로 룰의 최대 개입을 못 본다.** `normalize_action_minutes` 는
카드 수를 바꾸지 않는다 — 상한을 넘긴 **35개 leaf 가 조용히 다시 쓰였는데 폭포는 그것을
0 으로 기록한다.** F21 을 이 수치만으로 그리면 "룰이 거의 아무것도 안 했다" 로 읽히는데,
분(minute) 기준으로는 그렇지 않다.

**분 단위 before/after 를 기록하는 것이 다음 하네스 개선의 1순위다.**

### 3.1 "+0.15" 는 두 케이스가 만든 값이다

| | |
|---|---|
| `extend` 가 leaf 를 **더한** 행 | **5 / 102** — `busy-thin` 2행, `busy-overflow` 3행 |
| `shape` 가 leaf 를 **버린** 행 | 2 / 102 |
| 나머지 | **95행에서 ③층은 개수를 한 장도 안 바꿨다** |

**M18 이 1.0 미만인 행 대부분은 보충을 못 받는다.** 즉 §0 에 적었던 "룰이 커버리지 보충
에서만 참" 이라는 서술은 **이 데이터로는 지지되지 않는다** — 룰은 포화 블록(`busy_*`)의
두 케이스에서만 개입하고, 나머지 과소 생성은 그대로 최종 계획에 남는다.

⚠️ 초판 문서는 이 자리에 "룰이 마감 커버리지로 보충한다" 고 썼다. **폭포 원자료가 그것을
반박한다.** 독립 검토(2026-09-02)가 짚은 자리다.

## 4. 반복 3회 — 단회로는 결론을 낼 수 없었다

| 회차 | leaf | M17 micro | **M17 macro** | M18 중앙 | M18<1.0 | M19 | M25 |
|---|---|---|---|---|---|---|---|
| 0 | 447 | 0.953 | **0.824** | 0.946 | 27 | 0 | 0 |
| 1 | 447 | 0.987 | **0.912** | 0.950 | 30 | 5 | 0 |
| 2 | 448 | 0.982 | **0.882** | 0.938 | 28 | 1 | 0 |

**M17 macro 가 0.824~0.912 로 흔들린다.** 고친 하네스로 돌린 **단회 실행에서는 0.971 이
나왔는데, 3회 중 어느 회차보다도 높다** — 운 좋은 한 판이었다. M19 도 0→5→1 로 회차마다
다르다. **단회 수치로 이 지표들을 서술하면 안 된다.**

**케이스 판정 뒤집힘: 34개 중 9개(26.5%)** 가 회차마다 M17 통과/실패가 갈린다.

⚠️ **이 수치로 "그 9개가 경계에 있다" 고 말하면 안 된다.** 전 케이스가 동일한 확률
p=0.873 인 동전이라도 3회 중 뒤집힐 기대값은 34 × (1 − 0.873³ − 0.127³) ≈ **11.3개**다.
관측된 9개는 오히려 **우연보다 적다.** 이 데이터는 특정 케이스가 불안정하다는 증거를
담고 있지 않다.

말할 수 있는 것은 더 약하다 — **케이스를 단위로 본 95% 신뢰구간이 [0.794, 0.951]** 이라,
회차 간 0.824~0.912 차이는 **n=34 의 표본 오차 안**이다. 즉 "모델이 회차마다 흔들린다"
가 아니라 **"n=34 로는 ±0.08 밖에 못 좁힌다"** 가 맞는 서술이다. 초판의 "경계에 있다"
표현은 독립 검토 지적에 따라 철회한다.

⚠️ 안정적인 것도 있다 — **M25 는 3회 모두 0** 이고 **하한 미달도 3회 모두 0** 이다.

1차 실행(같은 날, 34호출)의 수치는 **전부 폐기한다.** 독립 감사가 찾은 것을 재현했다.

| 1 | **`review_feedback` 에 빈 문자열** | 프로덕션은 첫 분해에도 `"(첫 분해 — 이전 피드백 없음)"` 을 보낸다. **34호출 전부 프로덕션이 안 내는 프롬프트였다** |

| 3 | **micro 만 보고** | §5 가 이중 집계를 의무화. macro 0.873 vs micro 0.974 |

된다"* 고 써 뒀다.

## 6. 알려진 한계 — **보고서에 반드시 함께 싣는다**

### 6.1 지표가 "받아쓰기" 를 재고 있을 수 있다 (가장 큰 위협)

`focus_capacity`(M17 의 상한)·`total_minutes`(M18 의 목표)·`session_count_rule`(정확한
개수)이 **전부 프롬프트에 인쇄돼 LLM 에게 주어진다.** 그러면 높은 준수도는 "제약을
이해하고 지켰다" 와 "받은 숫자를 되돌려줬다" 를 구별하지 못한다.

계획서 §2 도 이미 경고했다 — *"그 이점의 절반은 문제가 쉬워서다 … 우리 그룹 A 는 대부분
제약을 하나씩 독립 체크한다."* TravelPlanner 가 어려운 이유는 제약이 **조합적으로
상호작용**하기 때문인데 우리 것은 그렇지 않다.

**실측이 이 위협을 강하게 지지한다.**

```
leaf 수 == llm_session_target :  101 / 102 = 0.990
요구 세션 길이보다 짧은 leaf   :  369 / 1210 = 0.305
계획별 (평균 길이 − 요구 길이) 중앙값 : −3.33분
```

**모델은 프롬프트에 인쇄된 세션 개수를 사실상 완벽하게 재현한다**(99%). 그러면서 각
세션을 조금씩 짧게 만든다. 이것이 "분량 미달" 의 기계적 정체다 — 개수는 받아쓰고 길이만
살짝 줄인다.

⚠️ **초판 문서는 여기서 "M18 이 받아쓰기 가설을 반박한다" 고 썼다. 그 논증은 무효다.**
32/34 케이스에서 프롬프트가 평균과 상한을 **같은 숫자**로 인쇄하므로, 개수를 지키고 상한을
안 넘으면 비율은 **정의상 1.0 이하**가 된다(88/102 행이 그 조건). 받아쓰기 상황에서 1.0
바로 아래가 나오는 것은 **예상되는 결과**이지 반박이 아니다. 독립 검토가 짚은 자리다.

**그래서 지금 데이터로는 "이해했다" 와 "받아썼다" 를 가를 수 없다.** 가르려면 프롬프트에서
`session_count_rule` 을 뺀 arm 이 필요하다(§8-4).

### 6.2 그 외

- **전 케이스 합성이다.** 실사용 인터뷰 슬롯 분포를 대표하지 않는다. 특히 `session_length`
  미답 경로가 실사용에서 얼마나 흔한지 모른다.
- **M20·M21·M22 미측정.** 배치(스케줄러) 결과가 필요한데 이번 하네스에 없다.
- **M26 미산출.** M17~M25 의 AND 인데 M18·M19·M24·M25 가 비율이고 "통과" 임계값을 §191 이
  사전 고정하지 않기로 했다. 분석 시점에 임계값을 정하는 것은 §0.1 정직성 규칙 1번
  위반이라 **내지 않는다.** 대신 M17·M19·M25 만의 동시 통과율(0.853)을 별도로 낸다 —
  **이것은 M26 이 아니다.**
- **§191 의 방향성 기준 두 개를 못 채웠다.** ①은 `normal` 블록의 M26 산출을 요구하는데
  M26 자체가 안 나온다. ②는 M24 를 ADR-0007 실측(2주기 12세션 중 9~12번)과 비교하라는
  것인데, 그 기준선은 **세션 단위**이고 M24 는 **branch 단위**라 단위가 다르다. 그리고
  마일스톤 케이스 6개 중 커서가 0 이 아닌 것은 1개뿐이라 **2주기 상황 자체가 거의 없다.**
- **3반복은 같은 날·같은 모델 버전·같은 설정에서 돌았다.** 모델 교체나 날짜 이동에 대한
  안정성은 모른다. 시드 통제도 없다(공급자가 제공하지 않는다).
- **`density` 는 전 케이스 `standard` 로 고정**돼 있고 골든셋에 그 필드가 없다.
  `light`/`intense` 는 주당 분량을 ±30% 바꾸는데 한 번도 안 돌려봤다.
- **마일스톤 블록 n=18(6케이스×3).** §2.2 의 macro 0.722 는 그 표본에서 나온 값이다.

## 7. 재현 방법

```bash
uv run python scripts/l1_7_run.py --dry-run          # LLM 없이 구조 확인

```

드러났다. 그것 없이 본 실행을 돌렸으면 34건 전부 폴백으로 돌고 "집계 대상 0건" 을 받았을
것이다.
