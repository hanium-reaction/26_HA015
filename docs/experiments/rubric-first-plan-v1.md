# 첫 계획 검토기 루브릭 v1 — 결함 5종 정의와 층 분업

> 짝 문서: [`experiment-plan-v1.md`](experiment-plan-v1.md) §2 L1-7.
> **이 문서가 "첫 계획의 결함이란 무엇인가"의 단일 진실 소스다.** 계획서 L1-7B 표의 한 줄
> 요약과 `prompts/planning/plan_quality.*.md` 의 체크리스트는 여기를 참조만 하고 재정의하지
> 않는다 — 정의가 두 곳으로 갈라지면 한쪽만 고쳐진다([`rubric-v1.md`](rubric-v1.md) 가
> L1-1 에서 같은 이유로 분리된 문서다).
>
> **한 정의, 세 용도**
> 1. **골든셋 결함 주입기의 사양** — `scripts/build_golden_first_plan_cases.py` 의
>    `seeded_defect` 블록이 여기 정의대로 결함을 심는다. M27~M31 의 분모가 된다.
> 2. **`plan_quality.v4` 체크리스트의 본문** — 검토기가 이 정의를 그대로 받는다.
> 3. **사람 라벨링 가이드** — 소표본 캘리브레이션(§6)에서 코더가 쓰는 기준.

---

## 0. 왜 이 문서가 필요한가

현행 `plan_quality.v3` 의 체크리스트는 **산문 6항목**이다. 앵커(무엇이 결함이고 무엇이
정상 편차인지의 경계)가 없어서 두 가지 문제가 있다.

1. **재현 불가능** — 채점자(LLM 이든 사람이든)마다 "구체성"·"중복"을 다르게 읽는다.
2. **오탐 비용이 실재한다** — 검토기 반려는 재분해를 트리거하므로, 헛짚으면 사용자가
   말한 값이 파괴되고 LLM 호출이 2배가 된다. 실제로 그렇게 됐다(§1).

## 1. 층 분업 규칙 — **④층은 ③층이 불변식으로 만든 속성을 검사하지 않는다**

이것이 이 루브릭의 **첫 번째이자 가장 중요한 규칙**이다. 파이프라인은 이렇게 흐른다.

```
② decompose_goal          LLM 원안
③ shape_action_plan 계열   결정적 룰 보정 — 여기를 통과한 시점에 성립하는 불변식이 생긴다
④ review_plan             LLM 검토기 — ③이 보장한 것을 또 보면 오탐만 남는다
```

### 1.1 실측 — v3 체크리스트 1·2번은 오탐 생성기다

`normalize_action_minutes` 는 모든 leaf 를 `[floor, session_min_for(outcome)]` 밴드로
클램프한다. 그리고 `_review_variables` 가 검토기에 넘기는 `focus_capacity` 는
**같은 함수** `session_min_for(outcome)` 의 값이다(`first_plan_adapter.py:1406`).
`extend_action_plan_to_horizon` 이 뒤에 붙이는 회차 세션도
`planned_session_min_for` = `max(10, min(derived, capacity))` 이라 상한을 넘을 수 없다.

슬롯 조합 **1,620건 전수 확인**(세션길이 9종 × 전역 집중시간 5종 × 주당시간 6종 × 빈도 6종,
프로덕션과 같은 보정 순서로 실행):

| v3 체크리스트 항목 | 보정 후 남은 위반 | 판정 |
|---|---|---|
| **1번. 세션 길이 상한 초과** | **0 / 1,620** | **구조적으로 발화 불가.** 이 항목의 모든 반려는 정의상 오탐이다 |
| **2번. 15분 미만** | 89 / 1,620 | 전부 `planned_session_min_for < 15` 인 조합(예: 주당 1시간 + 주 5~7회 → 10~12분). **룰이 의도적으로 허용한 값**이다 — 하한을 15로 올리면 그 계획의 평균 길이를 어떤 카드도 가질 수 없어 주당 예산이 카드마다 새기 때문(`normalize_action_minutes` 주석). 즉 **룰이 일부러 만든 것을 검토기가 반려한다** |

> **이 표는 핀 테스트로 고정돼 있다** — [`tests/test_first_plan_verifier_invariants.py`](../../tests/test_first_plan_verifier_invariants.py).
> `session_min_for` 나 클램프를 손대면 빨강이 된다. 뮤테이션 가드도 같이 있다(클램프를
> no-op 으로 만들면 1,620건 중 1,246건에서 실패하는 것을 확인했다) — 정상 데이터만 읽는
> 테스트는 `if False:` 로 바꿔도 초록이기 때문이다(`eval/README.md` 의 같은 원칙).

**따라서 120분 사고는 우발적 오작동이 아니라 1번 항목이 존재하는 한 반드시 나는 사고였다.**
사용자가 120분이라 답하면 `focus_capacity` 도 120분이고 모든 카드가 정확히 120분이 되므로,
검토기가 "상한을 넘었나"를 물으면 경계값에 딱 붙은 값을 보게 된다. 3/3 반려는 그 결과다.

### 1.2 규칙

> **④층 검토기는 아래를 검사하지 않는다. 프롬프트에 "검사하지 마라"가 아니라
> **변수 자체를 넘기지 않는** 방식으로 강제한다** — 변수가 있으면 지시를 어긴다(실측 다수).

| 검사하지 않을 것 | 이미 보장하는 곳 |
|---|---|
| 세션 길이 상한 | ③ `normalize_action_minutes` (불변식) |
| 세션 길이 하한 | ③ 〃 (하한은 의도적으로 가변) |
| 총 분량 / 주당 시간 준수 | ③ `shape_action_plan` → `_take_within_budget` |
| 세션 개수 / 케이던스 상한 | ③ `cadence_session_cap` |
| 목표 개수 한도(Focus ≤3 / Maintain ≤5) | ① `tier_violation_for` (LLM 분해 이전 게이트) |
| 고정일정·수면·no-touch 충돌 | 룰 스케줄러(애초에 그 시간을 피해 배치) |
| 이번 주기 범위 밖 단계 | ③ `drop_out_of_cycle_branches` |
| '외부 대기' 단계 | ③ `drop_waiting_steps` |
| 마감까지의 커버리지 | ③ `extend_action_plan_to_horizon` |

**남는 것은 룰이 원리적으로 판정할 수 없는 것 — 의미(semantics)뿐이다.** §2 의 5종이 그것이다.

⚠️ **`conflict_report` 는 검사 항목이 아니라 전달 항목이다.** 룰 스케줄러가 이미 판정한
결과를 사용자 친화 문장으로 옮기는 일이므로, 이걸 근거로 `approved=false` 를 내지 않는다.
반려는 §2 의 결함이 있을 때만이다.

## 2. 결함 5종 — 정의와 앵커

각 결함은 **정상 / 경계 / 결함** 3수준으로 앵커를 준다. 경계 수준을 따로 두는 이유는
두 가지다. ① 검토기에게 "애매하면 통과"의 기준선을 준다 ② 골든셋의 **난이도 격자**
(experiment-plan §2 L1-7B "경계값 격자 필수")가 이 수준에서 나온다.

> **채점 단위는 계획 1개다.** 결함이 한 건이라도 있으면 그 유형에 대해 결함 판정.
> 검토기는 유형별로 판정하고, 최종 `approved` 는 5종 전부 통과일 때만 참이다.

---

### D1. 중복 — 같은 일을 두 번 시킨다

같은 branch 아래에 **사실상 같은 작업**이 두 개 이상 있는가. 사용자에게는 진도가 안 나가는
계획으로 보이고, 실행하면 "이거 아까 안 했나" 가 된다.

| 수준 | 기준 | 예시 (같은 branch 안) |
|---|---|---|
| **정상** | 제목이 다르고 다루는 대상도 다르다 | "2강 자료구조 시청" / "3강 정렬 시청" |
| **정상** | 같은 대상이지만 **단계가 다르다** — 회독·복습·심화는 중복이 아니다 | "3강 시청" / "3강 예제 직접 풀기" |
| **정상** | `extend_action_plan_to_horizon` 이 만든 `N회차` 연속 세션 | "달리기 5회차" / "달리기 6회차" — **룰이 의도적으로 만든 것이다. 반려 금지** |
| **경계** | 대상이 같고 동사만 다른데 실질 작업이 겹치는지 불분명 | "3강 정리" / "3강 노트 작성" |
| **결함** | 제목이 표기만 다르고 대상·행위가 같다 | "3강 시청" / "3강 강의 보기" |
| **결함** | 완전 동일 제목이 2회 이상 | "GROUP BY 실습" / "GROUP BY 실습" |

⚠️ **`N회차` 오탐이 이 유형의 최대 위험이다.** 룰이 붙인 회차 세션은 제목이 거의 같으므로
중복 검사에 그대로 걸린다. 검토기에는 회차 세션을 **결함 후보에서 제외**하도록 명시한다.

---

### D2. 착수 불가 — 그것만 읽고 시작할 수 없다

**⚠️ v3 의 "SMART" 항목을 대체한다.** 근거가 탄탄한 것은 Locke & Latham 의 *"구체적이고
도전적인 목표"* — 즉 **S 하나**이고, SMART 5글자를 묶어 채점하는 검증된 도구는 없다
(Bjerke & Renger 2017 은 baseline 없이 A·T 판정이 불가능하다고 비판). 대신 **행동과학의
실행계획 척도**(Sniehotta et al. 2005 action planning: *when / where / how / how often /
with whom*)의 차원을 쓴다. 이 중 **when(③이 배치)·how often(M20 이 측정)** 은 이미
덮이므로, 검토기가 볼 것은 **what/how — 무엇을 어떻게 하는지**다.

| 수준 | 기준 | 예시 |
|---|---|---|
| **정상** | 대상 + 행위 + 범위가 있어 바로 시작 가능 | "정렬 알고리즘 3강 시청 후 예제 2개 직접 구현" |
| **정상** | 대상 + 행위. 범위는 세션 길이가 정한다 | "토익 LC Part 3 문제 풀기" |
| **경계** | 대상은 있으나 행위가 포괄적 | "3단원 공부" |
| **결함** | 대상이 없다 — 목표 제목의 재진술 | "영어 공부하기", "코딩 연습" |
| **결함** | 행위가 없다 — 상태·다짐 | "실력 향상", "꾸준히 하기" |

⚠️ **길이로 판단하지 않는다.** 짧아도 대상+행위가 있으면 정상이다("비자 수령 확인").
장황한 제목을 구체적이라고 읽는 것은 verbosity bias 다.

---

### D3. 순서 역전 — 뒤 단계가 앞 단계보다 먼저 온다

**앞 단계의 산출물이 있어야 뒤 단계가 성립**하는데 순서가 뒤집혔는가. 우리 파이프라인에서
`action_items` 의 순서는 곧 의도된 진행 순서다(`_take_within_budget` 이 "중간을 건너뛰지
않는다"를 그 전제 위에 세운다).

| 수준 | 기준 | 예시 |
|---|---|---|
| **정상** | 병렬 가능한 작업들의 순서 — 어느 쪽이 먼저여도 된다 | "단어 암기" 다음 "문법 정리" |
| **정상** | 학습 순서가 자료 목차를 따른다 | "1장" → "2장" |
| **경계** | 선후 관계가 있을 법하나 반대 순서도 말이 된다 | "모의고사 풀기" → "취약 유형 학습" (진단 후 학습이라면 정상) |
| **결함** | 산출물 의존이 명백히 역전 | "발표 리허설" → "발표 자료 작성" |
| **결함** | 마무리가 시작보다 앞 | "최종 제출" → "초안 작성" |

⚠️ **"이게 더 효율적이다"는 반려 사유가 아니다.** 명백한 **의존** 역전만 결함이다.

---

### D4. 착수 단서 부재 — `first_step` 이 제 역할을 못 한다

`ActionItemDraft.first_step` 은 이 제품 고유 필드로, 카드를 열었을 때 **5분 안에 시작할 수
있는 첫 동작**을 준다. 룰은 이 필드의 내용을 판정할 수 없다.

| 수준 | 기준 | 예시 |
|---|---|---|
| **정상** | 물리적으로 즉시 가능한 단일 동작 | "노트북 열고 3강 재생 버튼 누르기" |
| **정상** | 이어가기 세션의 복귀 단서 | "지난 회차에서 이어서 5분만 시작하기" (룰 생성분 — **반려 금지**) |
| **경계** | 동작이되 준비가 더 필요 | "자료 찾아보기" |
| **결함** | 제목의 반복 | 제목 "3강 시청" / first_step "3강 시청하기" |
| **결함** | 동작이 아닌 다짐·상태 | "집중해서 시작하기", "마음 잡기" |

---

### D5. 목표 무관 — 이 세션이 그 목표에 기여하지 않는다

행동과학 계획 품질 코딩의 **instrumentality**(도구성) 축이다 — 계획된 행동이 목표 행동과
실제로 연결되는가(van Osch et al. 의 이분 코딩). 룰은 제목 문자열만 보므로 판정할 수 없다.

| 수준 | 기준 | 예시 (목표: "정보처리기사 실기 합격") |
|---|---|---|
| **정상** | 목표에 직접 기여 | "SQL 활용 기출 3회차 풀기" |
| **정상** | 준비·보조 작업이되 목표 경로 위에 있다 | "실기 시험 접수하기" |
| **경계** | 기여가 간접적 | "타이핑 속도 연습" |
| **결함** | 다른 목표의 작업이 섞였다 | "토익 LC 문제 풀기" |
| **결함** | 목표와 무관한 일반 자기계발 | "아침 명상 10분" |

⚠️ **이 유형은 오탐 위험이 가장 높다.** 사용자의 접근 방식(`approach_note`)이나 참고
자료에 근거가 있으면 무관해 보여도 정상이다. **근거를 찾을 수 없을 때만** 결함으로
판정하고, 애매하면 통과시킨다.

## 3. 결함 주입 사양 (골든셋 생성기 계약)

`seeded_defect` 블록은 **무결함 기준 계획 1개를 고정**하고, 유형별로 **결함 1종만** 심는다.

| 유형 | 주입 방법 (결정적) |
|---|---|
| **D1** | 임의 leaf 하나를 복제해 제목의 동사만 동의어로 치환("시청"→"강의 보기"), 같은 branch 에 삽입 |
| **D2** | 임의 leaf 의 `title` 을 목표 제목의 재진술로 치환("{목표} 공부하기") |
| **D3** | 의존 관계가 명시된 인접 leaf 쌍의 `order_index` 를 맞바꾼다 |
| **D4** | 임의 leaf 의 `first_step` 을 `title` + "하기" 로 치환 |
| **D5** | 다른 카테고리 목표의 세션 1개를 삽입 |

**난이도 격자** — 유형마다 `easy` / `boundary` 2수준을 만든다. `boundary` 는 §2 의
**경계** 앵커에 해당하는 것을 심는다(반려하면 오탐, 통과가 정답). 이것이 계획서가 요구한
경계값 곡선의 재료다.

**무결함 대조군(`defect_free_control`)** — 아무것도 심지 않은 기준 계획. **M29
(`false_reject_rate`)의 분모다.** 여기에 반드시 포함할 것:

- 세션 길이가 `focus_capacity` 와 **정확히 같은** 케이스 (**120분 사고 회귀**)
- `planned_session_min_for < 15` 라 10~12분 카드가 정상인 케이스 (§1.1 의 89건 계열)
- 룰이 붙인 `N회차` 연속 세션이 포함된 케이스 (D1 오탐 회귀)
- 길이가 제각각인 케이스 (15분 확인 작업 + 120분 초안 작성 혼재 — v3 가 반려하던 정상 편차)

⚠️ **순환성 완화**: 계획서 L1-7B 가 못박은 대로, **이 루브릭을 쓴 사람과 다른 사람이 결함을
설계**한다(held-out fault design). 위 5종은 **실제 인시던트에서 채굴한 것**을 우선했다 —
120분 사고, `_WAITING_TITLE_RE` 백스톱이 생긴 #225, ADR-0007 범위 이탈 실측. 합성 규칙만으로
만든 결함은 실제 결함보다 탐지하기 쉬운 쪽으로 편향된다.

## 4. 검토기 출력 계약 (`plan_quality.v4`)

현행 `PlanReview` 는 `{approved: bool, feedback: list[str]}` 뿐이라 **PR curve 를 그릴 수
없고 운영점을 고를 수 없다**(계획서 L1-7B "운영점 보고"). v4 는 유형별 판정을 요구한다.

```json
{
  "findings": [
    {"defect": "D1|D2|D3|D4|D5",
     "severity": 1,
     "node_id": "<지목한 leaf>",
     "message": "<사용자 친화 제안 문장>"}
  ],
  "approved": true
}
```

- `severity` 1~3 (1=경계·통과 권고 / 2=결함 / 3=명백). **반려 임계값은 프롬프트가 아니라
  코드가 정한다** — 임계값을 바꿔가며 M27/M29 를 다시 계산해 운영점을 고르기 위해서다.
- `node_id` 가 **M28 `verifier_localization` 의 재료**다. 지금은 자유 문장뿐이라 "무엇을
  지적했는지"를 기계가 셀 수 없다.
- `findings` 가 비면 `approved=true`.

**톤 규칙은 v3 그대로 유지한다** — 사용자를 탓하지 않는 제안형, 금지어 동일.

⚠️ **`focus_capacity` · `session_length` 변수를 v4 에 넘기지 않는다** (§1.2). 변수를 주고
"보지 마라"고 쓰면 지킨다는 보장이 없다.

## 5. 채점 절차 — M27~M31 을 이 루브릭에서 계산한다

| 지표 | 이 루브릭에서의 계산 |
|---|---|
| **M27** `verifier_recall` | 유형별: 심은 결함 수 분의 `findings` 에 그 `defect` 코드가 severity ≥ 2 로 나온 수 |
| **M28** `verifier_localization` | 반려 건 중 `node_id` 가 **실제 주입 지점과 일치**한 비율 |
| **M29** `false_reject_rate` | `defect_free_control` 중 `approved=false` 인 비율. **≤ 0.10** |
| **M30** `replan_repair_rate` | 재분해 결과에 그 결함이 §2 기준으로 더 이상 없는 비율 |
| **M31** `replan_collateral_rate` | 재분해 전후로 **지적과 무관한** 값이 바뀐 비율 — 구체적으로 `estimated_minutes` 분포 / 총 분 / 마일스톤 branch 집합 중 하나라도 변한 케이스 |

⚠️ **M27 을 유형 평균으로 보고하지 않는다.** 어느 유형이 죽어 있는지가 정보이고, 평균은
그걸 숨긴다.

## 6. 알려진 한계

- **결함을 설계자 계열이 심는다.** §3 의 완화책(held-out 설계 + 실제 인시던트 채굴)을
  적용해도, **아무도 예상 못한 실패 유형은 이 루브릭으로 영원히 측정되지 않는다.**
  주기적으로 사람이 루브릭 밖에서 검토기를 깨보는 세션이 필요하다.
- **시딩 유효성 자체가 논쟁 중이다.** Just et al.(FSE 2014)은 뮤테이션 점수와 실결함
  탐지율의 강한 상관을 보고했지만 ICSE 2018 후속은 회의적이다. 양쪽을 병기한다.
- **D2·D5 는 의미 판정이라 사람 라벨 캘리브레이션이 필요하다.** 소표본(계획 20~30개)에
  사람이 유형별 라벨을 매기고 검토기와의 일치도를 **kappa 로** 본다. ⚠️ 단순 일치율은
  chance-corrected kappa 를 크게 과대평가한다(MT-Bench 기준 평균 38.6%p) — raw agreement
  로 보고하지 않는다.
- **이 루브릭은 "결함이 없다"를 보장하지 않는다.** 계획이 5종을 전부 통과해도 그 계획이
  달성 가능하다는 뜻이 아니다 — DCMA 14-point 에 대한 스케줄링 실무 문헌의 경고와 같다
  (계획서 L1-7A "구조적 결함 탐지 != 예측 타당도").
